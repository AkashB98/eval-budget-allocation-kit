# eval-budget-allocation-kit

**You have a fixed eval budget. Do you spend it on more questions, more trajectories per question, or more re-grades per trajectory? This kit answers that with a pilot, a textbook variance decomposition, and a held-out simulation — instead of a habit.**

Agent evaluations burn tokens at three nested levels: a new question costs a full rollout, an extra trajectory on the same question costs another rollout, and a repeat re-grade ("read") of an existing trajectory costs only the grading. Teams usually pick the split by folklore — five reads because a paper did, or one trajectory because it is cheap. The right split depends on *where the variance lives*: if questions differ a lot, buy questions; if the grader is noisy, re-grades genuinely pay. This repo builds the whole decision on a seeded synthetic agent (no LLM), estimates the three variance components from a pilot run, grid-searches the standard-error-minimising allocation under the budget, and then *verifies* the recommendation on held-out synthetic data against naive allocations spending the same budget.

> **Synthetic data only.** Every score is generated by a deterministic scripted agent (seeded, stdlib `random.gauss`). No real eval data, no LLM calls, no network, no API keys.

Stdlib-only Python 3. Zero third-party imports.

## Motivation

Motivated by Ning et al., *"Agentic RAG Evaluation: Budget Allocation Across Questions, Trajectories, and Reads"* (arXiv:2610.05034), which studies this allocation problem for agentic RAG evaluation. This kit is an independent, synthetic teaching/verification artifact: it does **not** reproduce that paper's experiments and does **not** claim its reported figures (e.g. 33% / 12.6%); every number below is produced by this repo's own seeded simulation.

## The headline: the folklore splits waste 11–32% of your precision

Planted truth (standard regime): between-question variance **0.04**, between-trajectory variance **0.09**, grader-noise variance **0.02**. Budget **200,000 tokens**; a rollout costs **1,000**, a re-grade **100**; the question pool is finite at **300**. A pilot of 100 questions × 3 trajectories × 3 re-grades estimates the components as **var_q 0.058286 / var_t 0.084454 / var_g 0.018883** — grader noise correctly identified as the small component.

| Allocation | Q × T × R | Cost | Held-out empirical SE |
|---|---|---|---|
| **Recommended** | **200 × 1 × 1** | 200,000 | **0.024614** |
| Repeats-heavy (5-reads style) | 142 × 1 × 5 | 198,800 | 0.027787 |
| Equal split | 90 × 2 × 2 | 198,000 | 0.028777 |
| Trajectories-heavy | 40 × 5 × 1 | 200,000 | 0.036340 |

At the same budget, the recommended allocation's empirical standard error is **11.4% below** the repeats-heavy split, **14.5% below** the equal split, and **32.3% below** the trajectories-heavy split (150 held-out simulations per allocation, separate seed; analytic true SE of the recommendation: 0.027386). With grader noise this small, re-grades are nearly free precision-wise to skip — every token goes to fresh questions, because between-question and between-trajectory variance dominate and only Q shrinks both.

## The kit is not rigged: when the grader is noisy, repeats win

Same machinery, second planted regime with grader-noise variance **0.25** (12.5× larger). The pilot sees it, and the recommendation flips: **Q=153, T=1, R=4**, empirical SE **0.031787**. Re-grading the same trajectory four times is now the correct spend. Eval G5 pins this so the optimiser cannot quietly be a "never repeat" heuristic.

## The failure case: a tiny pilot cannot be trusted

The recommendation is only as good as the pilot's component estimates. Averaged over 25 pilot draws each (headline eval G6):

| Pilot | Mean achieved true SE | Worst achieved true SE | Mean component relative error |
|---|---|---|---|
| Small: 20 questions | 0.027403 | 0.027812 | **0.251939** |
| Large: 200 questions | 0.027386 | 0.027386 | **0.097495** |

Honest read: the SE surface is flat near the optimum, so the *mean* damage from a tiny pilot is small (inflation 1.000621×) — the real damage shows up as **2.6× the component-estimation error** and a worse worst case. A 20-question pilot will confidently tell you the wrong variance story even when its allocation happens to land near the flat optimum. Size the pilot like you mean it.

## An honest note on the method

The method here is **not new, and this repo does not present it as new**. It is the textbook two-stage / optimal-allocation machinery from survey sampling and **generalizability theory**: a nested random-effects variance decomposition (between-question, between-trajectory-within-question, grader noise), estimated from a pilot by method of moments, then an exhaustive grid search for the allocation minimising

```
Var(mean) = var_q / Q  +  var_t / (Q·T)  +  var_g / (Q·T·R)
```

subject to the budget, the finite pool, and the unequal level costs

```
cost = Q·T·1000  +  Q·T·(R−1)·100
```

(a rollout's first grade is included; each extra re-grade costs 100). The contribution of this kit is the discipline around the standard method: a real simulated grader-noise level (never silently zero), a finite pool that forces budget into trajectories once questions run out (eval G7: a 2,000,000 budget caps at Q=300 and recommends T=6, R=2), held-out verification against naive splits at equal spend, a second regime where the opposite answer is correct, and a quantified small-pilot failure case.

## Quickstart

```bash
python3 cli.py report     # pilot -> components -> allocation -> held-out verification (JSON)
python3 cli.py check; echo $?   # 0 = recommendation beats all naive baselines on held-out sim
python3 demo.py           # end to end with asserts
python3 -m unittest discover -s tests   # 33 tests
python3 evals/run_evals.py              # 10 golden evals
```

`check` exit codes: **0** = the recommended allocation beats every naive baseline on held-out simulation, **1** = it does not, **2** = bad input (e.g. budget below one rollout, or a named input file that does not exist). `report` accepts `--budget` and `--regime {standard, high_grader_noise}`.

## How this maps to a customer POC

- **Pre-declared eval budget:** the customer fixes the token budget and the acceptance target ("mean agent score known to ±X") *before* anyone runs the full eval — the budget is an input, not a post-hoc invoice.
- **Allocation:** a small, deliberately-sized pilot estimates where the variance lives (questions vs trajectories vs grader), and the split of the remaining budget is chosen to minimise the standard error of the acceptance number — with the finite question pool and per-level costs stated up front.
- **Acceptance measurement:** the full eval runs the chosen allocation once, and the reported score ships with its standard error; the naive-split comparison is the counterfactual that shows what the same budget would have bought without the pilot. If the grader is the noisy level, the POC says so and spends on re-grades instead of pretending more questions fix a grading problem.

## Architecture

| Module | Job |
|---|---|
| `generator.py` | Seeded scripted agent: nested question / trajectory / grader-noise score model, two regimes, held-out simulation of an allocation's estimated mean |
| `allocator.py` | Exact cost accounting, method-of-moments variance components, exhaustive SE-minimising grid search, naive baseline shapes |
| `report.py` | Pilot → recommendation → held-out verification, high-grader-noise regime, small-vs-large pilot degradation study |
| `cli.py` | `demo` / `report` / `check` (exit 0/1/2) |
| `demo.py` | End to end with asserts: feasibility, baseline wins, repeats regime, pilot degradation, check gate |

## Evals

`python3 evals/run_evals.py` → **10/10 golden evals**, report committed at `evals/eval_report.json`:

- **G1** recommended allocation feasible: exact cost 200,000 ≤ budget, Q ≤ pool
- **G2** recommended beats all naive baselines on held-out empirical SE (0.024614 vs 0.027787 / 0.028777 / 0.036340)
- **G3** empirical SE tracks analytic true SE (0.024614 vs 0.027386)
- **G4** pilot recovers planted components, grader noise non-zero (0.018883 vs planted 0.02)
- **G5** high grader-noise regime: repeats DO help (R=4 recommended)
- **G6** small-pilot degradation: worse mean/worst achieved SE, 2.6× component error
- **G7** finite pool binds: 2,000,000 budget caps Q at 300, spends on T=6, R=2
- **G8** CLI `check` exit codes 0 / 2 / 2 (pass / bad budget / missing file)
- **G9** full report deterministic: same seed → identical report
- **G10** grader noise is a real level: high-noise pilot estimates var_g 0.25077 vs standard 0.020062

Unit tests: `python3 -m unittest discover -s tests` → **33 tests**, covering hand-computed cost accounting, component-estimation sanity on large pilots, feasibility across budgets (never over budget, never over pool), the grader-noise effect on SE, determinism (same seed → same report), CLI exit codes, and a no-network guard (sockets blocked).

## Scope and honest limits

- **Synthetic, planted variance.** The components are built in at known values, so "the recommendation wins on held-out sim" proves the machinery, not that a real agent's variance decomposes this cleanly. Real scores are bounded, skewed, and correlated in ways a Gaussian nested model is not.
- **Normal, independent noise.** Trajectory noise is modelled as independent of the question effect; a real agent may fail *systematically* on hard questions, which couples the levels and changes the optimal split.
- **The pilot costs budget too.** This kit reports the pilot design but does not deduct pilot spend from the allocation budget; a production version should optimise pilot + main split jointly.
- **Grid bounds.** The search caps T at 10 and R at 5 — stated conventions, wide enough that neither binds in the reported regimes.
- **Mean score only.** The estimand is the mean agent score. Pass-rate, worst-decile, or per-category estimands have different variance structures and different optimal allocations.

## Why this project

Forward-deployed evaluation work starts with a customer asking "how good is the agent, and how sure are you?" — under a budget they set. Answering with a folklore split wastes a third of the precision the budget could have bought, and quoting a number without its standard error is how evals get relitigated. This repo shows the pilot-first discipline end to end: measure where the variance lives, spend against it, verify on held-out data, and publish the failure case (the tiny pilot) next to the headline.
